## 1. 앱용 API 계약서 🆕

### 배경/문제
Flutter 앱을 별도 작업(세션)으로 만들기 시작했다. 앱 쪽이 컨트롤러·DTO 코드를 뒤지지 않고도 "이 화면엔 어떤 API 를 어떤 모양으로 부르나"를 알아야 했다.

### 선정 이유
엔드포인트 나열(Swagger)이 아니라 **화면별 매핑**으로 썼다 — 로그인 / 홈 / 친구 / 번개 발송 / 받은 번개·모임방. 앱 개발자는 화면 단위로 일한다. 그리고 문서를 상상으로 쓰지 않고 **실제 컨트롤러·DTO 기준**으로 작성.

### 구현/해결 내용
`docs/API_FOR_APP.md`(150줄): 화면별 필요 API + 요청/응답 필드, WebSocket(STOMP) 구독 경로·이벤트 형태, 토큰·에러·enum 규약(`dbb8c3a`). 08-27 기능 추가 때 같이 갱신(`7aaa017`). 이후 기능이 늘 때마다 이 문서를 고치는 것이 관례가 됐다.

### Before / After
| Before | After |
|---|---|
| 앱이 서버 코드를 직접 읽어야 함 | 화면별 API 표 한 장 |

### 테스트
문서라 테스트 없음. 앱이 이 문서만 보고 로그인~번개 화면을 붙였다(앱 정리본 07-30 ~ 08-18).

## 2. 친구 초대코드 — 검색 대신 코드 교환 🆕 🧭 🧪

### 배경/문제
앱의 친구 추가를 어떻게 할지. 백엔드에는 상대 userId 로 신청하는 API 만 있었고, 앱에서 상대 id 를 알 방법이 없었다.

### 선정 이유
| 대안 | 판단 |
|---|---|
| 닉네임 전체 검색 | 모르는 사람이 나를 찾을 수 있다 → **"닫힌 절친" 원칙**과 충돌 → 기각 |
| 연락처 동기화 | 권한 요청이 늘고 범위가 넓다 → 기각 |
| **초대코드 교환** | 코드를 직접 주고받은 사이만 연결 → 채택 |

코드 설계:
- 8자, **혼동 문자(0/O/1/I/L) 제외** 31자 알파벳(`ABCDEFGHJKMNPQRSTUVWXYZ23456789`) — 말로 불러 주거나 손으로 옮겨 적어도 틀리지 않게. 경우의 수 31⁸ ≈ 8.5 × 10¹¹
- `SecureRandom` 으로 생성, **필요할 때 처음 만든다**(지연 생성) — 가입 시점에 모두 만들 필요가 없다
- 코드를 넣으면 기존 `sendRequest` 규칙을 그대로 탄다 → 상대가 이미 나에게 신청했으면(맞신청) **즉시 ACCEPTED**

### 구현/해결 내용
- `User.inviteCode` + `assignInviteCode()`, `UserRepository.findByInviteCode / existsByInviteCode`
- `GET /api/friendships/invite-code` — 내 코드(없으면 생성)
- `POST /api/friendships/redeem {code}` — 앞뒤 공백 제거·대문자로 맞춘 뒤 코드 주인에게 신청
- 유일성은 당시 `ddl-auto: update` 라 DB 유니크 제약 대신 **앱 레벨**(존재 확인 후 재시도, 최대 10회)로 보장(`90ecf80`)

### Before / After
| | Before | After |
|---|---|---|
| 친구 추가 | 상대 userId 필요(앱에서 알 수 없음) | 8자 코드를 주고받아 신청 |
| 낯선 사람이 나를 찾을 수 있나 | — | 없음(검색 API 자체가 없음) |

### 테스트
`FriendshipServiceTest` 7개(`cb5ba6c`):

| 케이스 | 기대 |
|---|---|
| 코드가 없으면 생성 | 8자, 혼동 문자 없음 |
| 이미 있으면 그대로 | 재생성 안 함 |
| 없는 유저 | 404 |
| 빈 코드 | 400 |
| 없는 코드 | 404 |
| 본인 코드 | 400 |
| 정상 코드 | PENDING 신청 생성 |

### 남은 과제
- **아직 남음**: 유일성의 DB 보장 — Flyway 도입(09-02) 뒤 V1 스키마에도 `invite_code varchar(16)` 에 유니크 제약이 없다(10-15 확인). 지금도 앱 레벨 재시도로만 막는다. 동시에 같은 코드가 생길 확률은 31⁸ 공간이라 낮지만, 유니크 인덱스 추가(V6)가 깔끔하다
- 이후 처리됨: 틀린 코드 반복 입력 제한(10분 10회 → 429, 09-30, 앱 리포 `FEATURE_NOTES_2026-09-30_10-07.md` 4번)

## 3. "내가 띄운 번개" 조회 🆕 🐞 🧪

### 배경/문제
홈의 "내가 띄운 번개" 배너용. 번개를 보낸 사람은 `NEW_FLASH` 이벤트를 받지 않는다(받는 사람에게만 감). 그래서 **앱을 다시 켜면 내가 띄운 번개와 그 모임방을 찾을 길이 없었다**.

### 선정 이유
실시간 이벤트를 보낸 사람에게도 쏘는 대신, **조회 API** 로 해결. 이벤트는 접속 중일 때만 의미가 있고, 재시작 뒤 복원은 조회가 맞다.

### 구현/해결 내용
`GET /api/flashes/sent` — 내가 보낸 + ACTIVE + 만료 전 + **이미 시작된(예약 시각 도달)** 번개. `joinedMembers` 는 합류자만(보낸 사람 제외)이라 앱이 그 수로 "{N}명 모였어요"를 그린다. `SentFlashResponse`, `FlashRepository.findBySenderIdAndStatusAndExpiresAtAfter…`(`b9cc16f`).

### Before / After
| | Before | After |
|---|---|---|
| 앱 재시작 후 내가 띄운 번개 | 사라짐(이벤트를 못 받음) | 조회로 복원, 합류자 수 표시 |

### 테스트
`FlashServiceTest` 3개(`31d87f3`): 활성 번개를 합류자와 함께 반환 / **아직 시각이 안 된 예약 번개 제외** / 없으면 빈 목록.

### 남은 과제
- 이후 처리됨: 목록 N+1 제거(09-2x, 앱 리포 `FEATURE_NOTES_2026-09-22_09-29.md` 7번), 모임 수명 규칙에 따른 노출 기간(09-28, 같은 문서 11번)

## 4. 기본 활성 프로필 dev ⚙️ 🧭

### 배경/문제
로컬에서 IntelliJ 로 켜느냐 gradle 로 켜느냐에 따라 프로필이 달라져, 앱 개발 중 쓰는 **dev 로그인**(아무 문자열로 로그인하는 `DevSocialClient`)이 됐다 안 됐다 했다.

### 선정 이유
기본값을 dev 로 두면 로컬은 어떻게 켜도 동작한다. 대신 dev 프로필은 아무나 로그인되는 구멍이라 **운영에선 반드시 덮어야 한다** — 이 위험을 코드 주석이 아니라 CLAUDE.md "배포 전 체크리스트 0번"에 박았다.

### 구현/해결 내용
`application.yml`: `spring.profiles.active: ${SPRING_PROFILES_ACTIVE:dev}`(`eb24eb4`).

### Before / After
| | Before | After |
|---|---|---|
| 로컬 실행 방식에 따라 | dev 로그인 되거나 안 됨 | 항상 dev |
| 운영 | — | `SPRING_PROFILES_ACTIVE=prod` 로 덮어야 함(체크리스트 0번) |

### 테스트
기동 확인. 운영에서 실제로 막혔는지는 배포 준비 때 검증 — dev 로그인 401([`OPS_NOTES_2026-09.md`](OPS_NOTES_2026-09.md) 2번).
